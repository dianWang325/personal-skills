# 特性实际生效与回退的记录约定

对用户关注或日志涉及的每项特性建立 runtime_features 条目，不预设特性列表。名字用日志原文；具体触发条件以此次运行的证据为准，不套用其他版本的行为。

## 字段

| 字段 | 内容 |
|---|---|
| name | 特性名称，如用户所指的 CPP；不猜测缩写全称 |
| requested | 请求开启/关闭/自动、对应参数/环境变量和配置证据；没有配置证据时为 null |
| observed_status | enabled / disabled / fallback / mixed / unknown，均仅指 scope 中有证据覆盖的范围 |
| scope | 运行轮次、日志覆盖时段、阶段、rank/worker、请求/批次/shape 等适用范围及未覆盖部分；未知明确注明 |
| events | 按证据顺序保存初始化、生效、禁用、回退和恢复事件；每项含 timestamp（已知时）、phase、scope、event、reason、fallback_to、evidence_refs |
| evidence_refs | 实际状态对应的证据引用，例如 evidence 中的字段路径/ID、脱敏日志路径与行号或原文片段 |
| run_refs | benchmark/accuracy/tests 的对应 run_id；无法关联具体轮次时留空并记录限制 |
| impact | 对实验目的、测量范围、指标解释的影响与限制，不猜测回退造成的性能损失比例 |

## 判断规则

- enabled：执行阶段的证据确认特性在所述范围内生效；仅有 enabled=true 参数或初始化消息不足以确认测量阶段生效。
- disabled：日志明确实际禁用该路径；请求配置与实际状态仍分别保存。
- fallback：日志证实发生回退，原文原因和目标路径按已知保存，未知不能编造。scope 可以仅是一个请求或 rank，不据此推断整轮都回退。
- mixed：日志确认不同阶段、请求或 rank 使用不同路径，或先启用后回退/后续恢复；逐事件保留轨迹，不能用最后一条消息覆盖之前状态。
- unknown：缺少实际执行证据，或日志含糊/冲突无法消解。缺少警告不等于 enabled，也不能以性能数字推断生效。

日志中可搜索 fallback、fall back、disable、unsupported、not supported、条件不满足、回退及特性名称，但关键词只用于定位；必须阅读上下文，区分能力提示、条件分支说明与本次真正执行的回退。其他重试/进程的消息不能错配到本轮；无法确定来源则保留歧义。

日志只有局部片段、缺少部分 rank 或测量时段时，明确覆盖范围和缺失项。不自动探测远端或重跑实验来确认。

## 结果与复盘

结果摘要说明“请求开启 X，日志显示在某范围回退到 Y，原因 Z”，未知部分照实标注。索引中的特性状态仅作导航，详细范围以记录为准。压测/精度/测试结果按 run_refs 与事件关联；混合路径的整轮指标不能算作特性全程开启的结果。回退本身不自动把已完成的压测改为 failed；是否达到实验目的、实际运行状态和记录完整度分别描述。

比较特性收益时要求实际路径和证据范围可比。若特性可能回退但只有配置证据，应明确“实际是否生效未确认”，不声称特性收益已被验证。
